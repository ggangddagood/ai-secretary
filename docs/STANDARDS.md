# 표준과 규칙

> 작성 기준: 위반하면 무언가 깨지는 규칙만 (빌드 실패, 테스트 실패, 런타임 에러, 구조 파손). 위반 여부를 판정할 수 없는 문장은 규칙이 아니다. 취향("~하면 좋다")은 쓰지 않는다. 이유는 규칙이 직관에 반할 때만 덧붙인다.

## 검증 게이트

- 머지 전: `bash scripts/verify.sh` exit 0
- {추가 게이트 — 예: DB 마이그레이션 파일은 사용자 확인 없이 실행 금지}

## 모듈 경계

- {무엇이 무엇을 import하면 안 되는지.
  예: components/는 services/를 직접 import 금지 — app/의 라우트 핸들러를 통해서만 접근}

## 커밋/브랜치

- 커밋 메시지는 conventional commits (feat:, fix:, docs:, refactor:, chore:)
- {브랜치 규칙 — 예: 작업은 feat-<task> 브랜치에서, main 직접 커밋 금지}

## 네이밍/구조

- {예: 컴포넌트 파일은 PascalCase.tsx, 훅은 use*.ts, 서비스는 동사 중심 함수명}

## 환경 설정

- {예: 모든 환경 변수는 lib/env.ts에서 검증 후 사용. process.env 직접 참조 금지 — 이유: 누락된 변수가 런타임 깊은 곳에서 터진다}

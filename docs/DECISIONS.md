# 결정 기록 (ADR)

> 작성 기준: 실제 트레이드오프가 있었던 결정만. 판별 기준 — "같은 상황의 다른 팀이라면 다르게 선택할 수 있었나?" 아니라면 기록하지 않는다. 대안에는 구체적 기각 이유를, 결과에는 이 결정으로 불가능해진 것을 적는다.

## 철학

운영자 1명이 쓰는 무인 배치다. 고정 비용 0, 유지보수 표면 최소가 기본값이고, 그 위에 하나를
더 얹는다 — **조용히 죽지 않는다.** 사람이 매일 들여다보지 않으므로, 실패했을 때 실패했다는
사실이 도착하는 것이 성공했을 때만큼 중요하다.

---

### ADR-001: 전달 채널을 텔레그램 봇으로 한다

- **배경**: 운영자가 매일 읽을 채널이 필요했다. 국내 사용자에게 자연스러운 선택은 카카오톡이었다.
- **결정**: 텔레그램 봇 `sendMessage`. 봇 토큰 하나로 인증하고 만료가 없다.
- **대안**:
  - **카카오톡 "나에게 보내기"** — 기본 텍스트 템플릿이 200자 제한이라 브리핑 1건도 담기지 않는다.
    게다가 access token 6시간 / refresh token 약 2개월마다 재인증이 필요해, 무인 배치가 사람의
    재로그인을 기다리며 조용히 멈춘다. 철학의 "조용히 죽지 않는다"와 정면으로 충돌한다.
  - **이메일(SMTP)** — 만료 문제는 없지만 앱 비밀번호 관리와 스팸 처리 위험이 붙고, 짧은 브리핑을
    읽는 경험이 메신저보다 나쁘다.
- **결과**: 메시지 하나가 4096자로 제한되므로 렌더러가 항목 경계에서 분할해야 한다. 수신자는
  텔레그램 계정이 있어야 한다. 카카오톡 발송은 이번 범위에서 빠졌다.

### ADR-002: 실행을 GitHub Actions cron으로 한다

- **배경**: 하루 한 번 몇 분 도는 배치를 어디서 돌릴지 정해야 했다. 웹 화면도 수신 엔드포인트도 없다.
- **결정**: `.github/workflows/daily.yml` 의 `schedule` cron(`0 23 * * *` UTC = 08:00 KST) +
  `workflow_dispatch` 수동 실행.
- **대안**:
  - **VPS / 상시 서버 + crontab** — 월 비용과 OS 패치·모니터링이 붙는다. 1인 배치에 과하다.
  - **서버리스(Cloud Run, Lambda) 스케줄러** — 무료 티어로 가능하지만 배포 파이프라인과 로그
    확인 경로가 하나 더 생긴다. 코드가 이미 GitHub에 있는데 실행만 밖에 둘 이유가 없다.
- **결과**: 스케줄 정시 실행이 보장되지 않는다(러너가 붐비면 수십 분 지연). 실행 시간이 러너 쿼터를
  쓰므로 `timeout-minutes: 15`로 상한을 둔다. 리포지토리가 삭제·아카이브되면 배치도 멈춘다.

### ADR-003: 상태를 리포지토리 안 JSON 파일로 두고 워크플로가 커밋한다

- **배경**: 이미 보낸 항목을 다시 보내지 않으려면 실행 간에 남는 상태가 필요하다.
- **결정**: `state/seen.json`(URL sha1 → 발송 날짜)을 리포지토리에 두고, 실행이 **성공한 뒤에만**
  워크플로가 `chore: update seen state`로 커밋·푸시한다. 90일이 지난 항목은 저장 시점에 지운다.
- **대안**:
  - **관리형 DB(Postgres, Supabase 등)** — 레코드 수백 건짜리 키-값 맵 하나에 연결 문자열·마이그레이션·
    무료 티어 만료 관리가 붙는다. 얻는 것이 없다.
  - **GitHub Actions Cache** — 7일이면 만료된다. 90일 보존이 불가능하다.
  - **Gist / 외부 오브젝트 스토리지** — 토큰이 하나 더 필요하고, 상태 변경 이력이 코드 이력과 분리된다.
- **결과**: 발송 이력이 커밋 히스토리로 남아 "언제 몇 건 보냈는지"를 따로 만들지 않아도 조회된다.
  대신 워크플로에 `contents: write` 권한과 push가 필요하고, 동시 실행이 겹치면 push가 충돌하므로
  `concurrency: daily-brief`로 줄을 세운다. 실행마다 커밋이 하나씩 쌓인다.

### ADR-004: LLM을 선별 1회 + 요약 1회, 두 단계로 나눠 호출한다

- **배경**: 후보 수십 건에서 5건을 고르고 요약까지 만들어야 한다. 한 번의 호출로 둘 다 시킬 수 있다.
- **결정**: 1단계는 제목·출처·짧은 설명만 보고 선별(`curate`), 그다음 본문을 추출하고, 2단계에서
  **본문만 근거로** 요약(`summarize`)한다. 본문을 확보하지 못한 항목은 모델에 보내지 않는다.
- **대안**:
  - **1회 호출로 선별 + 요약** — 호출 비용과 지연이 절반이지만, 이 시점에 모델이 가진 것은 제목뿐이다.
    제목만 보고 요약을 쓰면 내용을 지어낸다. 브리핑에서 가장 치명적인 실패다.
  - **후보 전부의 본문을 먼저 추출한 뒤 한 번에 선별+요약** — 환각은 막지만 수십 개 사이트를 매일
    긁어야 한다. 5건만 필요한데 100건을 받아오는 낭비이고 실행 시간도 길어진다.
- **결과**: 호출이 2회로 늘고 파이프라인 단계가 하나 더 생긴다. 그 대가로 "본문 없으면 요약 없음"이
  구조적으로 보장된다 — 본문이 없는 항목은 애초에 프롬프트에 들어가지 않는다. 선별 단계는 제목만
  보므로, 제목이 부실한 좋은 글이 탈락할 수 있다.

### ADR-005: LLM을 Gemini 무료 티어(`gemini-3.6-flash`)로 시작한다

- **배경**: 시작 시점에 유료 API 결제를 하지 않기로 했다. 하루 호출은 2회뿐이다.
- **결정**: Google AI Studio 키 + `google-genai` SDK. 구조화 출력은 Pydantic 스키마를
  `response_format`(JSON Schema)으로 강제한다.
- **대안**:
  - **Anthropic Claude API** — 품질과 SDK 사용성은 좋았고 step 4 이전까지 실제로 이 구현이었지만,
    시작부터 카드 등록이 필요하다. 무료로 굴려 보자는 결정에 밀렸다.
  - **로컬 모델(Ollama 등)** — GitHub Actions 러너에서 매일 모델을 받아 돌리는 비용이 API보다 크다.
- **결과**: 무료 티어의 입력·출력이 제품 개선에 사용될 수 있다 — 보내는 것이 공개 기사 본문뿐이라
  감수한다. 한도·정책이 예고 없이 바뀔 수 있다. 교체가 필요하면 손댈 파일은 `llm.py` 하나이고,
  `make_client(cfg)`가 키 주입 지점이다.

### ADR-006: 수집 소스를 승인이 필요 없는 것으로만 제한한다

- **배경**: "AI 수익화·마케팅 정보"의 상당량은 Threads·X·Reddit에 있다.
- **결정**: Hacker News(Algolia), GeekNews RSS, GitHub Search API, 공개 RSS 피드만 쓴다. 전부
  인증 없이(또는 선택적 토큰만으로) 즉시 동작한다.
- **대안**:
  - **Threads 키워드 검색** — Meta App Review + 비즈니스 인증이 필요하다. 심사 기간이 개발 기간보다 길다.
  - **Reddit API** — 신규 OAuth 앱 수동 승인 대기가 반복 보고된다. 시작 시점을 남이 정하게 된다.
  - **스크래핑** — 마크업이 바뀌면 조용히 깨지고, 이용약관 위반 소지가 있다. 같은 이유로 GitHub
    Trending 페이지 대신 Search API를 쓴다.
- **결과**: 개인 창업자들의 1차 육성(voice)이 담긴 소셜 소스가 빠져 `money`/`marketing` 축의 후보가
  얇다. RSS 피드 목록으로 메우고 있으며, 축 편중은 `docs/tracking/FINDINGS.md`에서 추적한다.

### ADR-007: 주가 브리핑을 같은 리포지토리의 별도 파이프라인으로 만든다

- **배경**: 관심 종목의 종가와 급등락 이유를 매일 받고 싶어졌다. 이미 매일 도는 배치와 텔레그램
  봇이 있으니 어딘가에 얹으면 된다 — 어디에 얹느냐가 문제였다.
- **결정**: 같은 리포지토리 안에 `src/secretary/stocks/` 서브패키지와 CLI
  (`python -m secretary.stocks --market {us|kr}`), 워크플로 2개를 새로 만든다. 기존
  `secretary.main` 은 한 줄도 바꾸지 않는다. 두 파이프라인이 공유하는 것은 발송·HTTP·로깅
  약 154줄(전체의 11%)뿐이다.
- **대안**:
  - **기존 AI 브리핑에 소스로 추가** — 하드 게이트와 정면으로 충돌한다. AI 브리핑은 "본문 없으면
    요약 없음"과 "발송 성공 후에만 기록"이 전제인데, 시세에는 본문도 없고 중복 판정도 무의미하다
    (같은 종목을 매일 보내는 것이 목적이다). 게다가 엄선 5건 자리를 시세가 잠식한다.
  - **완전히 별도 리포지토리** — 도메인이 겹치지 않으니 깔끔해 보였다. 그러나 겹치는 11%가 하필
    **봇 토큰 마스킹 코드**다. 이 프로젝트에서 실제로 토큰이 한 번 유출됐고(ENGINEERING_NOTES),
    두 곳에서 관리하면 한쪽만 고쳐진다. 문서 하네스(`docs/` 9개 파일)도 통째로 복제된다.
- **결과**: 리포지토리의 정체성이 "AI 정보 배치"에서 "개인 비서"로 넓어졌다 — PRD와 README가
  두 배치를 설명해야 한다. 공유 코드가 갈리지 않도록 공용 모듈 2개(`tghtml.py`, `gemini.py`)를
  추출했고, 그 대가로 `render.py`·`llm.py`가 위임 레이어를 하나 갖게 됐다. `stocks/`가 기존
  도메인 모듈을 import 하지 못하도록 STANDARDS에 경계를 명시해야 했다.

### ADR-008: 시세를 Yahoo Finance v8 chart 직접 호출로 가져온다

- **배경**: 한국·미국 종목과 지수·환율을 한 번에 얻어야 한다. 계획 단계에서 무료로 쓸 수 있는
  소스 5개를 검토했다.
- **결정**: `https://query1.finance.yahoo.com/v8/finance/chart/{심볼}?range=1mo&interval=1d`
  를 심볼당 한 번 GET 한다. 인증이 없고 기존 `http.make_client` 를 그대로 쓴다.
  계획 단계에서 6개 심볼을 실제로 호출해 전부 HTTP 200을 확인했다.
- **대안**:
  - **KIS(한국투자증권) Open API** — 공식이고 국내 시세가 정확하지만, 증권 계좌 개설이 선행
    조건이고 접근 토큰이 24시간마다 만료된다. ADR-001에서 카카오톡을 기각한 것과 **정확히 같은
    종류의 함정**이다 — 무인 배치가 갱신에 실패하면 조용히 멈춘다.
  - **Twelve Data** — 무료 티어가 있지만 KRX 종목 포함 여부가 문서상 불확실했다. 확인하려면
    가입해서 실제로 호출해 봐야 하는데, 그렇게 얻는 것이 Yahoo보다 낫지 않다.
  - **Alpha Vantage** — 무료 티어가 하루 25요청이다. 심볼당 1요청 × (지수 3 + 관심 종목 N) ×
    하루 2회면 관심 종목 10개도 못 넣는다.
  - **pykrx** — KRX 데이터는 잘 주지만 미국 종목을 못 준다. 미국장 브리핑을 위해 소스를 하나 더
    붙여야 하고, 그러면 실패 지점이 둘로 늘어난다.
  - **`yfinance` 라이브러리** — 같은 Yahoo 데이터를 쓰지만 pandas를 끌어온다. 응답 파싱 100줄을
    아끼려고 무거운 의존성을 들이고, Yahoo가 응답을 바꿀 때마다 라이브러리 업데이트를 기다리게
    된다. 게다가 STANDARDS의 "외부 HTTP는 `make_client` 를 쓴다"를 우회한다.
- **결과**: 비공식 엔드포인트이므로 예고 없이 막힐 수 있다(v7/quote는 이미 막혔다). 막히면 조회
  실패 경로를 타므로 조용히 죽지는 않는다 — 전부 실패하면 실패 알림이 오고 exit 1이다. 교체가
  필요하면 손댈 파일은 `stocks/quotes.py` 하나이고, `parse_chart` 가 응답 스키마 의존을 모두
  안고 있다. 재시도 로직은 넣지 않았다 — 하루 두 번 배치라 다음 실행이 곧 재시도다.

### ADR-009: 관심 종목을 GitHub Actions Variables에 둔다

- **배경**: 관심 종목 목록은 사용자마다 다르고 자주 바뀐다. 어딘가에 저장해야 하는데, 이
  리포지토리는 **공개**다.
- **결정**: `STOCKS_WATCHLIST_US` / `STOCKS_WATCHLIST_KR` 를 GitHub Actions **Variables**에
  두고 워크플로가 `${{ vars.* }}` 로 주입한다. 코드에 기본값을 두지 않는다 — 환경 변수가 비면
  시장 지표만으로 브리핑을 만든다.
- **대안**:
  - **리포지토리에 커밋(설정 파일 또는 코드 상수)** — 가장 편하고 변경 이력도 남는다. 그러나
    공개 리포이므로 내가 무엇을 지켜보는지가 인터넷에 영구히 남는다. 보안 문제는 아니지만
    프라이버시 문제다.
  - **리포지토리를 private으로 전환** — 커밋해도 되게 만드는 방법이지만, 그러면 Actions가
    무료 2,000분/월 제한을 받는다(공개 리포는 무제한). 잘 돌던 AI 브리핑까지 비공개가 되고,
    공개 상태를 전제로 쓴 문서·ADR도 다시 봐야 한다. 종목 목록 하나 때문에 치를 값이 아니다.
  - **Secrets에 저장** — 위치만 보면 가장 안전해 보인다. 그러나 시크릿이 아닌 값을 넣으면
    GitHub이 로그에서 그 문자열을 `***` 로 덮는다. 어떤 심볼이 조회에 실패했는지 로그로 볼 수
    없게 되고, 종목명이 흔한 단어면(예: `애플`) 무관한 로그 줄까지 가려진다.
- **결과**: 종목 변경 이력이 남지 않는다 — 언제 무엇을 넣고 뺐는지 되짚을 방법이 없다. 종목을
  바꾸려면 `gh variable set` 을 쓰거나 리포지토리 설정 화면에 들어가야 하고, 로컬 실행에서는
  `.env` 에 같은 값을 따로 넣어야 한다(두 곳이 어긋날 수 있다). 대신 Variables는 마스킹되지
  않으므로 Actions 로그에서 심볼별 조회 결과를 그대로 읽을 수 있다.

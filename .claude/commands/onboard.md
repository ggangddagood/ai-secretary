기존 프로젝트에 이 프레임워크의 문서 하네스를 구축한다. 코드베이스를 이해하고 docs/를 실제 내용으로 채우는 온보딩 작업이다.

## 원칙

- **저장소에서 관찰한 것이 곧 프로젝트의 진실은 아니다.** 코드는 현재 구현을 보여주지만 의도를 증명하지 못한다.
- **추론은 틀렸을 때의 비용에 비례해서 쓴다:**
  - 기술적 사실(구조, 진입점, 빌드/테스트 방법, 의존성) → 코드에서 직접 도출해 기록한다
  - 제품 규칙, 비즈니스 정책, 보안 의도, 운영 가정 → 소유자(사용자)에게 확인한다. 예: 인가 체크의 현재 동작은 코드로 확인되지만, 그것이 의도한 전체 정책인지는 코드가 증명하지 못한다
- **기존 문서는 자동으로 권위를 갖지 않는다.** 코드와 대조해서 유지/개선/병합/폐기를 결정한다. 서로 모순되는 두 서술을 둘 다 남기지 않는다 — 정본(코드/매니페스트가 "현재"의 근거, 사용자가 "의도"의 근거)에서 하나로 정리한다.

## 절차

1. **탐색**: 구조, 진입점, 인터페이스, 데이터 경계, 테스트, 배포 방식을 파악한다. 필요시 Explore 에이전트를 병렬로 쓴다.
2. **검증 명령 확인**: 프로젝트의 실제 빌드/테스트/린트 명령을 찾아 `scripts/verify.sh`를 채우고, 실행해서 통과를 확인한다. 실패하면 그 상태 자체를 사용자에게 보고한다 (조용히 넘어가지 않는다).
3. **기존 진입 문서 처리**: 기존 CLAUDE.md/AGENTS.md가 있으면 `.backup/`으로 백업한 뒤 내용을 비판적으로 검토한다 — 그대로 옮겨 적지 않는다. 각 내용이 새 구조의 어느 문서에 속하는지 분배하고, 무엇을 어디로 옮기고 무엇을 왜 버렸는지 사용자 승인을 받는다.
4. **소유자 확인**: 코드로 증명할 수 없는 항목(도메인 규칙의 의도, 보안 정책, 운영 제약, 하드 게이트 후보)을 모아 질문한다. 한 번에 4개 이하.
5. **docs/ 작성**: 각 문서 상단의 작성 기준을 따른다. 코드만 읽으면 알 수 있는 것은 쓰지 않는다 — 의도, 제약, 이유, 함정만. 해당 없는 문서(예: UI 없는 프로젝트의 UI_GUIDE.md)는 삭제한다.
6. **AGENTS.md 채우기**: placeholder를 실제 내용으로. 하드 게이트는 소유자 확인을 거친 3~5개만.
7. **자가 점검**: 코드에 있는데 문서에 없는 것(누락), 문서에 있는데 코드에 없는 것(환각), 근거 없는 주장이 없는지 양방향으로 대조한다. 이 대화를 모르는 다음 에이전트가 문서만으로 작업할 수 있는가.
8. 사용자 승인 후 완료. 이후는 일반 `/plan` → `/build` 사이클을 쓴다.

## 경계

이 작업은 문서를 만드는 작업이다. 커밋 생성, 브랜치 변경, 코드 수정을 시작할 권한으로 해석하지 않는다 (`scripts/verify.sh` 작성은 예외).
